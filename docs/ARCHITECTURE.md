# Diorama architecture

Every folder has one job, and `npm run check` enforces the rules below for a project.

## Repository

```
diorama/
├── core/                 the engine, imported as @core, @core/draw, @core/volume, @core/rig
│   ├── draw/             flat 2D drawing used inside volumes, effects and the HUD (README.md is its guide)
│   ├── volume/           volumes, camera, space profile, scenery, navigation, effects
│   ├── rig/              skeletons, clips, characters, gear, items
│   └── *.ts              asset contract, random, noise, colors, sheet packing, HUD pieces (ui.ts), index
├── packages/             what games and the viewer share to play the exports (README.md in each)
│   └── runtime/          @diorama/runtime: the atlas contract in pure TypeScript, no DOM, no dependencies
├── docs/
│   ├── ARCHITECTURE.md   this file
│   ├── guides/           how-to guides, by module: volume/, rig/ (the draw guide is core/draw/README.md)
│   ├── api/              reference, generated by `npm run docs:api` (never edited)
│   └── media/            images the README shows (the banner)
├── tools/                command line (cli.ts, project.ts, layout.ts, lint.ts, typecheck.ts, kits.ts) and exporter (export.ts, runners)
├── scripts/              doctor and the API docs generator
├── templates/            what `new-project` copies: project/src/theme.ts, optional/STYLE.md
├── tests/
│   ├── run.ts            runs the suites below (npm test)
│   ├── engine/           core (draw, interface assets), volume, rig and the dependency boundaries
│   ├── docs/             snippets, links and paths of the markdown
│   ├── runtime/          the runtime package: its rules, standalone compile, contract types, conformance traces
│   ├── viewer/           viewer logic
│   └── cli/              commands, including the layout check
├── viewer/               the app (src/) and its dev server (server/)
├── examples/             Soulkeeper, the sample game (examples/soulkeeper); its assets/ and review/ are not versioned
├── projects/             your projects, one folder each: not versioned by Diorama (only projects/README.md);
│                         each project can be its own git repository
├── .agents/skills/       instructions for coding agents
├── .claude/              launch.json for the viewer, and the third-party skills used on the viewer
└── README.md, LICENSE, THIRD_PARTY.md, .gitignore, package.json and package-lock.json, tsconfig.json, vite.config.ts,
    index.html (the viewer's entry), dev.sh and dev.bat (start the viewer and open it), components.json and skills-lock.json (shadcn, for the viewer)
```

Commands and the viewer find a project by name in `projects/` first, then in `examples/`; `projects/<name>` or `examples/<name>` names one folder exactly. Generated files are never versioned: `assets/` and `review/` of every project, `node_modules/`, builds. `npm run example` exports the sample after a fresh clone.

The module guides live in [docs/guides/](guides/README.md) and answer "when do I use this"; the generated [API reference](api/) answers "what is the exact signature". The skills in `.agents/skills/` route an agent to both.

### Dependency direction

```
draw  <-  volume  <-  rig                 core/: the engine, the producer of the files
```

```
@diorama/runtime          imports nothing (not core/, not the DOM)
    ^
  viewer (the Playground, the previews), and games                 the players of the files
```

- Core and the runtime share no code: they share the exported JSON (the atlas contract). Core writes it and the runtime reads it; `tests/runtime/contract.test.ts` checks that core's producer types fit the runtime's.
- `@diorama/runtime` (`packages/runtime`) imports only its own files: no `core/`, no package, no `node:` module, and no DOM (its `tsconfig.json` has lib ES2022 alone). Code outside `core/` reaches it through the `@diorama/runtime` alias (`tsconfig.json`, `vite.config.ts`), never by a path into `packages/`.
- `draw` imports no other engine module (only the low-level `random`, `noise` and `color` of `core/`); `volume` imports `draw` and never `rig`; `rig` imports `volume` and `draw`.
- The top-level files of `core/` (`asset.ts`, `ui.ts`, `random.ts`...) import neither `volume` nor `rig`; the HUD helpers of `ui.ts` build on `asset.ts`, and the HUD pieces a project writes with them draw with `draw`.
- `core` never imports `tools/`, `viewer/`, `packages/`, `projects/`, `examples/` or `tests/`: nothing outside `core/`.
- Projects, examples and templates import the engine only through `@core`, `@core/draw`, `@core/volume` and `@core/rig`, never a path inside `core/`; the tools, the engine's own tooling, may also import its files by path. Nothing imports an `internal/` folder.
- The viewer reaches the engine only through the same `@core` aliases.
- Nothing imports `tests/`.

`tests/engine/boundary.test.ts` checks every line above.

## A project

```
<project>/                      projects/<project>/  or  examples/<project>/
├── STYLE.md                    art direction: palette, proportions, line, light, reference sizes
├── src/                        hand-written code; nothing here is exported by itself
│   ├── theme.ts                palettes, ramps, strokes, materials (VOLUMES), CAMERA
│   ├── space.ts                space profile: grid, scale against the characters, walls
│   ├── characters/
│   │   ├── shared/             clip factories, skeletons and skins used by several characters, and a body plan
│   │   │                       kept apart from its character (the sample's wolf and spider bodies)
│   │   └── <id>/               character.ts, spec.ts, outfit.ts, skeleton.ts, clips/<clip>.ts, and the helpers its clips share
│   ├── gear/                   parts by family + catalog.ts + index.ts
│   ├── scenery/                pieces by family + catalog.ts + index.ts
│   ├── scenes/                 scene layouts (data) and the map
│   ├── vfx/                    effects by family + catalog.ts + index.ts
│   ├── items/                  item pieces + catalog.ts + index.ts
│   └── ui/                     HUD pieces and their drawing helpers
├── sheets/                     one entry per exported sheet: a thin file that imports from src/ and exports it
│   ├── characters/<id>/<clip>.ts
│   ├── props/<id>.ts
│   ├── scenes/<id>.ts
│   ├── ui/<id>.ts
│   ├── gear/<part>.ts          generated by `npm run gear-items`
│   ├── scenery/<piece>.ts      generated by `npm run scenery-items`
│   ├── vfx/<effect>.ts         generated by `npm run vfx-items`
│   └── icons/<item>.ts         generated by `npm run item-icons`
├── assets/                     exported PNG + atlas JSON, mirroring sheets/ (generated, never edited)
└── review/                     contact sheets, scenery tests, mockups, scratch (never versioned; safe to delete)
    ├── contact/                npm run contact
    ├── scenery-tests/          npm run scenery-test
    └── mockups/                npm run export -- <project> <sheet> --mockup
```

Soulkeeper, the sample game (`examples/soulkeeper`), has every part of this tree: five characters, a gear kit, a scenery kit with four scenes, effects, item icons and 11 HUD pieces, 165 sheets. `characters/necromancer/` is not one of the five: it is a flat illustration of Malvek (a portrait and an idle loop, drawn with `@core/draw` alone and exported with `defineAsset`), so it has no clips, skeleton or manifest.

### The four places

| Place | It is | Written by | Versioned |
| :--- | :--- | :--- | :--- |
| `src/` | the code: drawings, kits, catalogs, characters, scenes | you and your agent | yes |
| `sheets/` | the list of what gets exported: one thin file per sheet | you (hand-written sheets) and four commands (generated sheets) | yes |
| `assets/` | the output: PNG and atlas JSON, at the same path as their sheet | `npm run export` | no |
| `review/` | scratch for looking: contact sheets, scenery tests, mockups | `contact`, `scenery-test`, `export --mockup` | no |

A project root holds only these four, `STYLE.md`, an optional `README.md`, the optional `diorama.config.json` (export options) and a `.gitignore`.

### Sheets

A sheet is a `.ts` file under `sheets/` whose default export is one asset. It does no drawing: it imports the asset from `src/` and exports it (or, in one call, builds it from a `src/` catalog or scene with `defineTileSet` or `defineSceneAsset`, as the generated sheets and the scene sheets do).

```typescript
export { crate as default } from '../../src/props/crate';
```

Hand-written sheets are made by `new-asset`, which writes the drawing in `src/<subpath>.ts` (a named export) and the sheet in `sheets/<subpath>.ts`. A character is written once in `src/characters/<id>/character.ts` (`defineCharacter`); each clip is a one-line sheet, `sheets/characters/<id>/<clip>.ts`, that exports `character.sheet('<clip>')`.

Generated sheets are one per entry of a kit's catalog. Each starts with a `// Generated by npm run <command> from src/<kit>/catalog.ts` line and is rewritten by its command (`--force`), never edited:

| Folder | Command | From |
| :--- | :--- | :--- |
| `sheets/gear/` | `npm run gear-items` | `src/gear/catalog.ts` |
| `sheets/scenery/` | `npm run scenery-items` | `src/scenery/catalog.ts` |
| `sheets/vfx/` | `npm run vfx-items` | `src/vfx/catalog.ts` |
| `sheets/icons/` | `npm run item-icons` | `src/items/catalog.ts` |

The names of a sheet's states and clips join with `--` (`scenery/crypt-door--open`).

### Kits

A kit is a folder of `src/` that describes a set of related assets as data: `gear/`, `scenery/`, `vfx/` and `items/`.

- `catalog.ts` is what an editor (a person, an agent, the viewer) reads and writes: one entry per piece, with its ids, labels, options and sizes.
- `index.ts` is what other code imports: it re-exports the pieces a character, a scene, another kit or a sheet needs, so they write `../gear` and not a path inside the kit. A catalog that has to import the characters it describes (`gear/catalog.ts`) stays a module of its own, which is imported by name.
- The other files are the pieces, grouped by family (`walls.ts`, `floors.ts`, `weapons.ts`), one concept per file.

`npm run new-kit -- <project> scenery|gear|vfx|items` starts a kit: it writes `catalog.ts`, `index.ts` and a first piece in a family file, with the engine's types and the project's `CAMERA`, `VOLUMES` materials and space profile (`src/space.ts`, when there is one). It refuses to overwrite a kit's files unless `--force`.

| Kit | First piece | Then |
| :--- | :--- | :--- |
| `scenery` | a crate prop in `props.ts` (`SCENERY`) | `scenery-items`, export `scenery/`, `scenery-test`; `new-scene` and the viewer's scene painter work on it |
| `gear` | a helm in `heads.ts`, a mannequin body in `bodies.ts` (`CATALOG`, and `CHARACTERS` with a mannequin that wears the helm) | `gear-items`, export `gear/`; the viewer's customizer and `new-outfit-character` work on it |
| `vfx` | a spark burst in `bursts.ts` (`VFX`) | `vfx-items`, export `vfx/` |
| `items` | a gem in `gems.ts`, with two rarity tiers (`ITEMS`) | `item-icons`, export `icons/` |

The first piece is a block-out that renders, so the kit's command, the export and `npm run check -- <project> --strict` pass on it at once; then it becomes the project's own, and the next pieces are added to the family files and the catalog by hand. `npm run check -- <project>` reports a `catalog.ts` that has no `index.ts`. [Guide 04 §5](guides/volume/04-scenery-kits.md) lists what a scenery catalog needs at least, and the catalogs of the sample's kits (`examples/soulkeeper/src/<kit>/catalog.ts`) are the full form.

### Where a new thing goes

| You are adding | Write | Then |
| :--- | :--- | :--- |
| A prop, a mark, a one-off asset | `npm run new-asset -- <project> props/crate --engine volume` (writes `src/props/crate.ts` and `sheets/props/crate.ts`) | `npm run export -- <project> props/crate` |
| A character | `npm run new-asset -- <project> characters/hero/walk --engine rig` (writes `src/characters/hero/character.ts` and the clip's sheet) | add the other clips, export `characters/hero/` |
| The first scenery piece, gear part, effect or item of a project | `npm run new-kit -- <project> scenery\|gear\|vfx\|items` (writes `src/<kit>/catalog.ts`, `index.ts` and a first piece) | the kit's command, then export that folder |
| A scenery piece, a gear part, an effect, an item | its drawing in the kit's family file, its entry in `catalog.ts` | the kit's command (`scenery-items`, `gear-items`, `vfx-items`, `item-icons`), then export that folder |
| A scene | `npm run new-scene -- <project> <name> --scene <file.json>` (writes `src/scenes/<name>.ts` and its sheet) | export `scenes/` |
| A HUD piece | its drawing in `src/ui/<piece>.ts`, a one-line sheet in `sheets/ui/<piece>.ts` | export `ui/` |
| A color, a stroke, a material, the camera | `src/theme.ts` | `npm run check -- <project>` |
| The size of a cell, a wall, a door | `src/space.ts` | `npm run check -- <project>` |

## Rules

Checked by `npm run check -- <project>` (type errors, then the layout rules, then [determinism](#determinism)) or by `npm run layout -- <project>` alone. Every message names the file and what to move where.

1. **Four places.** `src/` is code, `sheets/` is what gets exported, `assets/` is output, `review/` is scratch. A project root holds only these, `STYLE.md`, an optional `README.md`, `diorama.config.json` (which holds only `outDir`, `scale`, `format`, `cols` and `gap`) and `.gitignore`.
2. **No naming tricks.** Everything in `src/` is a module and everything in `sheets/` is a sheet; no underscore prefixes.
3. **Thin sheets.** A sheet imports from `src/` (or `@core`) and exports one asset; it declares no function or class and has at most 20 lines of code. Generated sheets keep their "Generated by" line.
4. **One direction.** `src/` never imports `sheets/`; sheets never import other sheets.
5. **Mirrors.** Every sheet has its exported image in `assets/` at the same path (and the atlas JSON next to it: a single static image, like the sample's `characters/necromancer/portrait.png`, has none), and every asset has its sheet.
6. **Names.** Folders and files are kebab-case (markdown notes in `src/`, like `README.md`, may use capitals); one concept per file; a kit folder with a `catalog.ts` has an `index.ts`.
7. **Outputs only.** `assets/` holds only PNG (or JPEG) and JSON; `review/` is never read by the viewer or the exporter.

Rules 1 to 4, 6 and 7 are errors. Rule 5 is a warning, because a fresh checkout has no `assets/` yet and an edited sheet has not been exported yet; `npm run layout -- <project> --strict` (or `npm run check -- <project> --strict`, which type checks first) makes it an error, which is the gate to run after an export.

### Determinism

The same source exports the same pixels. `npm run check -- <project>` reports, with the file and the line, what breaks that in the code of `src/` and `sheets/` (comments do not count):

- `Math.random`, and `createRng()` without a seed (its default seed is the clock): variation comes from `createRng(seed)` of `@core` with a fixed seed (`pieceRng(ctx)` of `@core/volume` in a scenery piece, `effectRng(ctx, salt)` in an effect);
- the clock, `new Date`, `Date()`, `Date.now` and `performance.now`: animation follows `frameIndex` and `frameCount` (or a clip's `t`);
- raw color literals (`#hex`, `rgb()`, `rgba()`, `hsl()`, `hsla()`) outside `src/theme.ts`: colors are theme tokens (`PALETTES`, `RAMPS`, `VOLUMES`), and a kit piece reads the material of its role (`ctx.materials.<role>.ramp`).

They are errors. `src/theme.ts` holds the palette, so its color literals are the only ones allowed.

### Type errors stop the export

`npm run export` runs the type check of `npm run check` first (the project's `src/` and `sheets/`, about 2 s for the sample, once per run) and exports nothing while the project has a type error; `--force` skips it for experiments. `scenery-test`, a review render, skips it too.

## What enforces what

| Rule | Enforced by |
| :--- | :--- |
| The layout of a project (the seven rules above) | `npm run check -- <project>` and `npm run layout -- <project>`; `tests/cli/cli.test.ts` breaks each rule on purpose and checks the message, and checks that `examples/soulkeeper` follows them |
| Determinism (no `Math.random`, no clock, no raw colors outside `src/theme.ts`) | `npm run check -- <project>` (`tools/lint.ts`); `tests/cli/cli.test.ts` writes each pattern and checks the message, and checks that `examples/soulkeeper` passes |
| No export from code with type errors | `npm run export` (`tools/typecheck.ts`, shared with `check`); `tests/cli/cli.test.ts` checks the refusal and `--force` |
| A new kit works with its commands | `tests/cli/cli.test.ts` runs `new-kit` for each kit, its generator, `new-scene`, the export and `check --strict` |
| The dependency direction, the public entrypoints, nothing imports `tests/` | `tests/engine/boundary.test.ts` (scans every import of `core/`, `packages/`, `tools/`, `scripts/`, `viewer/`, `templates/`, `examples/` and `projects/`, and those of `tests/` for paths into `packages/`) |
| The runtime compiles alone (lib ES2022, no DOM, no dependencies) and core's producer types fit its contract types | `tests/runtime/standalone.test.ts`; `tests/runtime/contract.test.ts` (it compiles itself, and is part of `npx tsc --noEmit -p .`) |
| Snippets in the guides and skills compile; every markdown link, heading link and backticked repository path exists | `tests/docs/docs.test.ts` |
| The engine, the runtime, the commands and the viewer's logic | `tests/engine/`, `tests/runtime/` (with conformance traces of the sample's characters, `tests/runtime/conformance/`), `tests/cli/`, `tests/viewer/` |

`npm test` runs all five suites through `tests/run.ts` (every `*.test.ts` under `tests/engine/`, `tests/docs/`, `tests/runtime/`, `tests/viewer/` and `tests/cli/`, in that order, then a summary of which passed); `npm run test:engine`, `test:docs`, `test:runtime`, `test:viewer` and `test:cli` run one. A test file outside those folders fails the run, so a new test cannot be left out.

CI (`.github/workflows/ci.yml`) runs both type checks and `npm test` on every pull request and on `main`. `main` is protected: changes land through pull requests, which merge only when CI passes.

## What reads what

```
src/  <-  sheets/  --export-->  assets/  <--  viewer, games
                        \--contact, scenery-test, --mockup-->  review/
```

- The exporter imports each sheet, renders it in headless Chromium and writes `assets/` at the sheet's path. It never reads `assets/` or `review/`.
- The viewer shows the exported `assets/` of every project and loads the kits in `src/` for its editors (the customizer and the scene painter); what it saves goes through the commands (`new-outfit-character`, `new-scene`), so it lands in `src/` and `sheets/` like any hand-written file. It never reads `review/`.
- A game reads `assets/`: the PNG and the atlas JSON next to it (`meta.data` carries the contract, see [rig guide 04](guides/rig/04-atlas-contract.md)). `@diorama/runtime` reads and plays the JSON for it; the viewer's Playground plays its characters and effects with the same package, and still places effects on screen with its own pixel arithmetic, which a test holds to the runtime's positions ([packages/runtime/README.md](../packages/runtime/README.md)).
