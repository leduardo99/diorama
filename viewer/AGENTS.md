# Diorama viewer

React SPA on the TanStack stack (Router, Query, Table, Store), served by Vite at `/viewer/`.
Its API is the `diorama-api` plugin in `vite.config.ts`; the filesystem logic (catalog, delete, trash, restore) is in `viewer/server/`.

## Projects and paths

- Projects come from `projects/` (yours) and `examples/` (the samples that ship with Diorama), found by `tools/project.ts` like the commands do: a name in `projects/` hides an example of the same name. The server says where each lives (`ProjectMeta.root`, `.rel`; `AssetFileMeta.root`): the project picker marks examples with an "example" badge, and a sample is never deleted as a whole (the project's ⋯ menu leaves "Delete project" out and the server refuses). Every API is keyed by the project's name; the root is only for building paths.
- A project is `src/` (code), `sheets/` (one file per exported sheet: every `.ts` there is a sheet), `assets/` (the exports, at their sheet's own path: `sheets/gear/helm.ts` → `assets/gear/helm.png`) and `review/` (scratch: the viewer never reads it). `viewer/server/catalog.ts` reads `sheets/` and `assets/`; `src/` is read for what a sheet imports and for the kit catalogs. Paths and URLs are built with `lib/project-paths.ts` (`projectDir`, `projectFile`, `projectUrl`, `kitCatalogUrl`, `sceneUrl`), never by hand: files are served at `/<root>/<project>/...` (`/examples/soulkeeper/assets/gear/helm.png`).
- A project may have a game, `game/index.html` (rule 8 of `docs/ARCHITECTURE.md`), which the server reports as `ProjectMeta.hasGame`: the project bar's "Play game" and the ⋯ menu's "Open game" open it in a new tab with a plain `<a target="_blank" rel="noopener">` to `projectUrl(root, name, 'game/')`, never a router `Link` (the game is a page of its own, not a route of the viewer).
- The kit catalogs the viewer imports are `src/gear/catalog.ts` (`CATALOG`, `CHARACTERS`) and `src/scenery/catalog.ts` (`SCENERY`); saved scenes are `src/scenes/<name>.ts` (`SCENE`). `src/vfx/catalog.ts` and `src/items/catalog.ts` are read by the commands that write `sheets/vfx/` and `sheets/icons/`, not by the viewer, which shows effects and item icons from their exported atlases. Exported folders: `characters/<id>/`, `props/`, `scenes/`, `ui/`, and the generated `gear/`, `scenery/`, `vfx/`, `icons/`.
- The viewer's deletes go to `<repo>/.diorama-trash/` (`assets/<project>/<id>/` for assets and sheets, `projects/<id>/<project>` for a project), outside every project: a project root holds only `src/`, `sheets/`, `assets/`, `review/` and a few files (`npm run check`). Restoring an asset refuses when the project of that name now lives elsewhere.

## Conventions

- Routes are file-based in `src/routes/`. `src/routeTree.gen.ts` is generated: never edit it by hand. In `vite.config.ts` the router plugin must stay before the React plugin. A path under a project that matches no section (`/p/soulkeeper/nope`) reaches the project's `notFoundComponent`, which says "Page not found"; "Project not found" is only for the `notFound({ data })` its `beforeLoad` throws.
- The app shell is a header, not a sidebar (`components/app-header.tsx`): logo, the project switcher (`project-switcher.tsx`: a Popover with shadcn `Command`, search, asset counts, "New project", ⌘K; switching keeps the section the user is in, `lib/sections.ts`), the project's ⋯ menu (`project-menu.tsx`: new asset, export, open game, copy path, delete) and New / Refresh catalog / Shortcuts and the language switch (`language-switch.tsx`) on the right. The project's own bar (`routes/p.$project.tsx`) holds its section tabs, its totals and Play game (when `hasGame`) / Export / New asset. Pages fill the space under the header (`flex min-h-0 flex-1 flex-col`), nothing scrolls but their own scroll element.
- The URL is the state of a project's asset list (search, sort, filters, view, grouping, open preview). Search params are validated with zod in `src/lib/search.ts`; components read them with `getRouteApi` (`src/lib/routes.ts`), never with casts.
- Server state lives in TanStack Query (`src/lib/queries.ts`, `src/lib/mutations.ts`). Callbacks that must outlive a menu or dialog go on `useMutation`, not on `mutate()`.
- Table is v9, not v8: `features` and `columns` are module-scope (`src/lib/asset-columns.tsx`), sorting and filters are controlled from the URL (`src/lib/use-asset-table.ts`).
- UI is shadcn/ui (radix base, `mira` preset, Tailwind v4): components live in `src/components/ui/` and are added with `npx shadcn@latest add <name>`, never written by hand. The shadcn CLI is not a dependency of the project (npx downloads it on each use; the components here were added with 4.22.1, so `npx shadcn@4.22.1 add <name>` matches them). The stylesheet the components need, which the package used to provide as `shadcn/tailwind.css`, is copied into `src/styles/shadcn-tailwind.css` and imported by `styles/app.css`; when components come from a newer CLI, copy that version's `dist/tailwind.css` over it (keep the header) and update the version there and in `THIRD_PARTY.md`. Load the `shadcn` skill (`.claude/skills/shadcn`) before touching UI and follow its rules: semantic colors, `gap-*`, `data-icon`, Field/FieldGroup for forms, AlertDialog for destructive confirms, Empty/Alert/Badge/Skeleton instead of custom markup.
- React rules: load the `vercel-react-best-practices` skill (`.claude/skills/react-best-practices`, a copy of `vercel-labs/agent-skills` at commit `063bee9`; rules in `rules/*.md`) before writing or changing components. What matters most here: gesture and pointer state in refs (`rerender-use-ref-transient-values`), derived values during render and not in effects (`rerender-derived-state-no-effect`), functional `setState`, lazy `useState`/`useHistory` initializers, `memo` only where a re-render was measured to cost (the palette rows, the canvas), stable callbacks for memoized children, no components defined inside components, non-passive `wheel` only where `preventDefault` is needed.
- Modals are `@ebay/nice-modal-react` modals in `src/modals/`: open them from anywhere with `NiceModal.show(Modal, props)`; the single `NiceModal.Provider` is in `routes/__root.tsx`. Bind a shadcn Dialog with `useModalDialog()`.
- Toasts are `sonner` (`toast()`); there is no custom toast store.
- **Interface language** (`src/i18n/`): English by default and Brazilian Portuguese; the header switch (`language-switch.tsx`) is remembered in `localStorage` (`diorama.lang`) and sets `<html lang>`. The Phaser test bench reads the same key for its footer (`packages/phaser/demo/footer.ts`), so keep its name. **Every interface string goes through `t()`, with its key in both dictionaries**: `en.ts` is the source of truth (nested keys, `as const`) and `pt-BR.ts` is typed against its shape, so a missing or extra key is a type error. Labels, buttons, tooltips, `aria-label`s, `title`s, placeholders, toasts, errors, empty states, the sentences the viewer writes (the wield notes) and units all count; English copy is sentence case with no exclamation marks. `tests/viewer/i18n.test.ts` checks the keys, the `{placeholders}`, the plurals and that no Portuguese is left hard-coded in `src/` (its `ALLOWED` list takes text that is legitimately content).
  - In components: `const { t, plural, number, date, relative, bytes, list } = useT()`, with `t('key', { name })`, `plural('counts.assets', n)` (a key with `.one` and `.other`, picked by `Intl.PluralRules`) and the formatters: never `toFixed` or `toLocaleString` by hand. A sentence with `<code>`, `<kbd>`, `<b>` or `<mono>` in it is rendered by `<Rich id="..." />`, never cut in pieces in the JSX.
  - Pure code in `lib/` that writes text takes a translator (`wieldReport(..., translator)`, `groupLabel(t, group)`), so a test picks the language with `createTranslator('pt-BR')` (`i18n/core.ts`: no React, no DOM); code outside a component (a thrown error, a toast from a callback) uses `currentTranslator()` from `i18n/store.ts`. A memo that holds text lists `t` in its dependencies.
  - What comes from the project's data (catalog labels, item and scene names, the engine's messages, the server's errors) is content: shown as it is, never put in the dictionaries. The shadcn `dialog`, `sheet`, `spinner` and `breadcrumb` read their screen-reader texts with `useT()`: put that back if one is added again with the CLI.
- Tailwind only scans `viewer/src` (`source("../")` in `styles/app.css`). Do not widen it: scanning the repo reloads the page on every edit elsewhere.
- The `diorama-api` plugin redirects a game's address without its slash (`/projects/my-game/game`) to `game/`, and the Phaser test bench's (`/packages/phaser/demo`) to `demo/`: Vite would serve the repository's root page for them, which sends you to the viewer. Edits under `packages/phaser/` reload only the test bench and the projects' game pages (`handleHotUpdate`).
- `handleHotUpdate` in `vite.config.ts` keeps edits to projects (`projects/`, `examples/`), `core/`, `templates/` and `tools/` from reloading the viewer; a reload would drop the toasts that carry Undo. After editing `core/`, reload the page by hand.
- The playground (`src/lib/playground/*`, `src/components/playground/*`) reads only exported atlases (when the project has a game, a line under its toolbar says the Playground plays the exports with debug tools and `game/` plays them in Phaser, with a "Play game" link) and follows the action contract in `docs/guides/rig/04-atlas-contract.md`: a character is `meta.data.character` (manifest with `controls`) or, for old atlases, a folder + `meta.data.skeleton` + `meta.pivot`; clips are classified by `meta.data.clipKind`/`action`/`key`/`tags`/`hold`/`travel`/`sockets`/`events` (fallback: `groundSpeed`/`loop`), never by file name. Keys come from `controls` (WASD, Shift = last of `move`, 1..9 = `actions` in order, H hit, K death, R reset). The state machine is the runtime's (`@diorama/runtime`, `packages/runtime/src/actor.ts`, in floor world units: priority death>hit>actions>locomotion>idle, an action is replaced only from its `cancel` event, hit/death interrupt anything, `hold` freezes until reset, `travel` follows the facing the action started with); `actor.ts` puts its actors in the view (`view.ts` gives each one `x`, `y` in actor units, projected with its character's camera at its export scale; a point the view sets (a spawn, a drag, a move it clamps) reads back exactly, and `vfx.ts` draws an effect where the view draws the frame that cued it (on its socket: the actor less the pivot plus the socket × scale), moves a projectile by its velocity in actor units, turns its impact to the heading that velocity shows and sorts an effect at `y + lift`, so half pixels, the draw order's ties and an impact's row come out as they did in px; `currentFrame` pivots the rectangle the view draws (without `meta.pivot`, the middle of its bottom, trimmed or not); a clip moves its sprite at its own `meta.scale` and a projectile flies at its effect sheet's; the view's sides are kept by `sideRoom`; `startClip`, `stepPlayer` and `advance` emit the events the runtime returns) and `effects.ts` draws events: `hit` rings at the weapon socket (`tip`, else `mouth`, else `hand`), `release` sends a projectile from `spawn:<socket>` (it ends after 150 logical px or when it leaves the scene, with a ring where it landed), and skills tagged `aoe` draw nothing because their sheet already has the rings. The looping base clip fires its own events (`step:<leg>`) so the HUD shows them (frames are 0-based, as in the manifest). The scene toolbar has a time scale (1×, ¼×, ⅒×, Pause) to read frames and events; it is never persisted and a badge (click to reset) shows whenever it is not 1×. The rules are tested in `tests/runtime/actor.test.ts`, the view and the rings in `tests/viewer/playground.test.ts`. The runtime moves at `groundSpeed` world units per second and the view draws that at `× meta.scale` with the vertical part multiplied by `sin(camera.tilt)` (manifest `camera`, default 48°; root motion too), so the feet stay planted in every direction while the facing row still follows the input's angle; facing maps the heading to `meta.directionFacings`. `meta.data.character` is a manifest object on character sheets but only the wearer's id (a string) on gear items (`role: 'gear'`): the runtime reads it through `manifestOf` and keeps gear items out of characters (they are objects to place); `library.ts` hands the server's asset list to the runtime's `readSheet` and `buildLibrary`. The palette (`placement-list.tsx`) is virtualized with TanStack Virtual and its search/grouping logic is pure (`lib/playground/catalog.ts`, tested in `tests/viewer/playground.test.ts`); things on the scene are picked by pixel alpha, dragged, and edited through `SceneHandle`.
- The asset grid and table are virtualized with TanStack Virtual (720 assets mount ~15 cards): `AssetsView` owns the scroll element and passes `scrollRef` to both lists; the grid lays out whole rows (`useGridColumns` gives columns and card width, as `auto-fill` would) and the table uses spacer rows under a sticky header. Each list scrolls its own active entry into view; `useEntrySelection` only moves the key.
- The asset list filters by type (`role` in the URL: Characters, Items, Scenery, Props, Effects, Icons, Interface, Other), read from the atlas (`atlasInfo.role`, `part`, `label`, `group`, `kind`, `rarity`, `stack` in the catalog; `lib/asset-role.ts`). Effects (`role: 'vfx'`, `meta.data.effect`), item icons (`'icon'`, `meta.data.item`) and interface pieces (`'ui'`, `meta.data.kind`) each stand alone in the list even though their folders (`vfx/`, `icons/`, `ui/`) hold many animated sheets (`lib/groups.ts: STANDS_ALONE`); an icon's card shows its rarity tier in the project's color, its kind and its stack, an effect or interface card its kind, and an effect plays on hover like any animated sheet. `roleDetail` is the badge text of every role. A gear item is titled by its label, carries its group as a badge, and its thumbnail is the piece cut out of its cell.
- Each asset has an engine, read from the imports of its sheet and of every local file that chain reaches in `src/`, to its end (`tools/sources.ts: createSourceReader`, which `viewer/server/catalog.ts` shares with `npm run export -- --changed`; a sheet is thin, the drawing is several imports deep): `rig` (`@core/rig`: characters, gear, item icons), else `volume` (`@core/volume`: props, scenery, effects), else none (no sheet, or a sheet that reaches neither). The asset list filters and sorts by it (`engine` in the URL, `EngineBadge`) and the "New → Asset" form offers exactly these two: volume asks for size and fps, rig for a skeleton and a clip and runs `new-asset --engine rig` (the first clip of a character folder creates `src/<folder>/character.ts`; every asset has a sheet in `sheets/<subpath>.ts`, and a volume one its drawing in `src/<subpath>.ts`; subpaths are kebab-case). The viewer shows the assets through the engine's own previews (asset preview dialog, playground, customizer, scenery painter).
- Export state comes from the server catalog: `AssetFileMeta.sourceMtime` (newest of the sheet and the `src/` files it imports, however deep) vs the image's `mtime` gives `isStale` (the rule, with its second of slack, is `tools/freshness.ts`: `export --changed` exports exactly the stale and pending sheets), and `ProjectMeta.pendingSheets` lists sheets with no image at their own path (`src/lib/export-state.ts`, covered by `tests/viewer/catalog.test.ts`; `AssetFileMeta.sheet` is the sheet's path under `sheets/`). `ExportBanner` and `PendingExportModal` export them one by one through `useExportSources`.
- Changes under `viewer/server/` are loaded by `vite.config.ts` at startup: restart `npm run view` after editing the catalog or the API.
- The customize tab (`src/components/customize/*`, `src/lib/outfit/*`) dresses characters with the project's gear kit and previews them live with the real engine: `drawCharacterFrame`, `outfitFromData` and `validateOutfit` from `@core/rig`. The kit is `<root>/<p>/src/gear/catalog.ts` (exports `CATALOG` and `CHARACTERS`), loaded lazily by dynamic import of its path, only when the server catalog says it exists (`ProjectMeta.hasGearKit`, `lib/outfit/catalog.ts`): a kit created while the viewer runs shows up at the next refresh (`import.meta.glob` would not see a file created after the dev server started); a project without it gets an explanation, and `?fixture=true` loads the built-in kit (`lib/outfit/fixture.ts`) to develop without one. Outfit edits are pure functions (`lib/outfit/edit.ts`, tested in `tests/viewer/outfit.test.ts`); drafts live in memory per project and character. A skin is a function: never hand one to `setState` directly (React would call it as an updater), wrap it as `setSkin(() => skin)`. The preview repaints only when the outfit, clip, frame, facing or zoom change, and the eight-direction strip paints one direction at a time. "Save as character" posts `new-outfit-character` to `/__api/cli` (the plugin writes the outfit to a temp file for `tools/cli.ts`) (it writes `src/characters/<name>/{outfit,character}.ts` and `sheets/characters/<name>/<clip>.ts`) and then exports `characters/<name>/`. Parts are loaded when the page opens: reload it after editing the kit. Material roles split in two (`splitRoles`): the kit lists a part's roles with their fallbacks (`['metalAccent', 'metal']`), so a role that extends another of the list is a refinement and lives in a folded "Advanced" section. Exported gear items (`gear/<part>.png`, from `sheets/gear/<part>.ts` written by `gear-items`; `meta.data.role = 'gear'` with `part`, `label`, `group`) are the pickers' thumbnails (the SE_0 cell cut to its drawn pixels, `lib/trim.ts`) and show in the asset list as "Items"; "Update items" posts `gear-items` to `/__api/cli` and exports the folder only when something is missing or stale.
- **Customizer by slot** (`components/customize/slot-board.tsx`, `part-picker.tsx`, pure model `lib/outfit/slots.ts`, tested in `tests/viewer/slots.test.ts`): the default "Slots" tab lists the places the skeleton has (`slotsOf` from the engine: a wolf has no hands; places the kit has nothing for are left out), each with what is worn there, so swapping is one click. A piece's row opens `PartPicker` (shadcn `Command` in a popover, its list computed only while open: search; "Similar" are the engine's `swapCandidates`, the same `equip` slot when the kit sets it, else the same group resting on the same kind of part, then "Others"; "Take off piece"; for a pair the "On both sides" switch). The edits are the engine's (`swapPiece`, `equipPart`, `removePiece` from `@core/rig/outfit-edit.ts`, guide 05 "Editing outfits": the rules a game shares when it equips an item), wrapped in `lib/outfit/slots.ts` to return `null` instead of throwing and to add what a screen needs: `swapPiece` keeps the piece's place, side, **id** and host, the materials by role and the options by key (numbers clamped, selects validated); what rested on it stays when it needs no host (a belt on a tunic that becomes a tabard) or accepts the new part, and an add-on that cannot rest on it goes, with a toast and "Undo"; `removePiece` frees the pieces that did not need their host instead of removing them. The wrapper asks `swapBlocker` before a swap: a part whose `equip` slot another piece keeps is a candidate marked `taken` ("Slot taken by …", disabled; the engine's `swapPiece` throws on it), and one that needs the hands (a two-handed weapon beside a shield) is not refused but done with `equipPart`, which takes the other hand's piece out (`pushed`, said in the picker as "Takes … out of the hands" and in the toast with "Undo"). The engine also puts a piece after a host that comes later in the list. An empty place offers "Equip" (`equipOrSwap`: a part with `equip` replaces the piece that keeps that slot, one without stacks as a layer; an add-on needs its `requires` host worn and is disabled with "Needs: …"; a part whose `equip` another piece keeps is "Slot taken by …"). The engine's vocabulary is the contract: `slotsOf`, `isPairedSlot`, `partRequires` (`requires` is a string or a list), `partKind` (body parts and flourishes are folded away and stay in the "List" tab) and `equip` (`validateOutfit` rejects two pieces in one equipment slot, per side for a pair). The property tests run every swap and every equip the picker can offer, for every character of the real kit, through `validateOutfit`, so a kit change that breaks a rule fails there instead of in the UI. Every edit goes through `useDraft` (a `useHistory`: undo/redo buttons and ⌘Z / ⇧⌘Z / Ctrl+Y, sliders merge into one step with a merge key). **Weapons** (`lib/outfit/wield.ts`, tested in `tests/viewer/wield.test.ts`): a held part says its class (`PartInfo.wield`), a character's attacks say the classes they are made for (`CharacterClip.wields`), each hand (slots hand and forearm) holds one part with `wield`, and after every edit `wieldReport` (the engine's `checkWield` in the words of the screen) tells in an alert above the pieces when no clip is made for what is held or a held item is never swung; the preview's clip picker marks the clips made for something else (they still play there) and the save dialog lists the clips the new character will not get (`new-outfit-character` only generates the usable ones). The test keeps the report and the engine agreeing on when there is something to say, over every swap the picker offers. The viewer has no use for socket data (`weaponSockets` is applied when the character is exported), and the playground never plays a clip the manifest marks `usable: false` (the runtime's `buildLibrary`, `packages/runtime/src/gear.ts: playableClips`). The "List" tab keeps the full per-piece editor (order, host, slot, side); body and materials sit in a folded block under the slots.
- The scenery tab (`src/components/scenery/*`, `src/lib/scenery/*`) paints scenes of the project's scenery kit (`src/scenery/catalog.ts` exports `SCENERY`; `?fixture=true` loads `lib/scenery/fixture.ts`) the way a game lays them out. Saved scenes are `src/scenes/<name>.ts` (`SCENE`; a helper beside them, like `map.ts`, exports no `SCENE` and is not a scene), found through the server catalog (`hasSceneryKit`, `scenes`). Edits are pure functions on `SceneData` (`lib/scenery/edit.ts`, which asks the engine for `footprintOf` and `cellPiece` so both always agree) and a drag is a pure stroke (`lib/scenery/gesture.ts`: `startPaint`/`startSweep`/`startMove`/`startMoveWall`/`startMoveFigure`, `advance` for each new cell, `resultOf` for what is committed); both are tested in `tests/viewer/scenery.test.ts`. **Nothing re-renders React while the pointer moves**: `SceneCanvas` keeps the stroke, the hovered cell, the scene on screen and the pending frame in refs, draws the main canvas with the engine's cached renderer (`createSceneRenderer`, one per catalog: frames already drawn are copied, so an edit costs about 1 ms of JS) and the overlay (`lib/scenery/overlay.ts`: grid, hover cell, selection, and the ghost of the prop being placed or dragged, copied from `renderer.frame`) in one `requestAnimationFrame` per change, and commits the gesture once with `onCommit` when the pointer is up (one undo step: `use-history.ts` has no begin/end). A click that places a prop or fills is drawn in the next frame and committed at once. What the canvas reports (hovered cell, last drawing time, drawing error) goes to a TanStack Store (`lib/scenery/status.ts`, read by `canvas-readout.tsx` and the painter's alert with `useSelector`), so only those readouts re-render. Keep it that way: no `setState` in pointer handlers, no `useEffect` that redraws per edit, handlers passed to the memoized `SceneCanvas` and `SceneryPalette` must be stable (`useCallback`). The drawing scale is `render.ts: renderScale(zoom × devicePixelRatio)`, capped at the export scale (2): the canvases keep their size in CSS pixels through `zoom` and `image-rendering: pixelated` upscales them, so a retina screen at 2× zoom still draws 2 device pixels per logical pixel, not 4 (a quarter of the memory and of the cold-frame cost; sprites stay crisp). Sprite coordinates (`hit.ts`, rims, anchors) are in drawing pixels, so convert them to CSS pixels with `zoom / scale`, never with `1 / devicePixelRatio`. Changing the scale drops the renderer's cache, so a change of zoom that moves it draws every frame again once; the renderer holds at most 800 frames (`limit`). Hiding a layer leaves it out of the drawing, not out of the scene. Palette thumbnails are the pieces drawn by the engine in small scenes with a shared renderer, one per task (`thumbs.ts`), so they never go stale and do not hold the page. **Layout** (as in Tiled, LDtk, Godot and Unity): a panel on the right with only the pieces (the three brushes at a glance, then a grid of pieces by group; Tab or the toolbar button hides it, the choice is a preference), a toolbar (the scene menu first: a popover with open, new blank scene, size and materials, named after the scene with a dot when it is unsaved; then undo, layer eyes, zoom, grid, panel, shortcuts, save), the tool-options bar (what the tool in use is armed with: piece, facing, variant, the eraser's layer, and a one-line hint), a tool rail down the left of the canvas, and a status bar (hovered cell, size, scene name with "unsaved"). **Nothing above or below the canvas may change height with the tool or the state** (the cell under the pointer would move): the toolbar (`h-12`), the tool-options bar (`h-12`) and the status bar (`h-8`) are single lines of a fixed height, never `flex-wrap`; when narrow, the toolbar drops the words of the layer toggles and of Save (container queries `@3xl`/`@2xl`), the options bar cuts its hint (full text in a tooltip) and what still does not fit scrolls horizontally (scrollbar hidden), and the draw/scene alert is absolutely positioned over the canvas, never a row above it. Keep it that way when adding controls: measure the canvas box's `getBoundingClientRect().top` across every tool, with the panel open and closed and with the alert shown. There is no selection tab: selecting a prop (select tool, or Alt/Cmd-click with any tool) opens a popover over it (`selection-popover.tsx`, anchored to the prop's picture measured from the renderer's frame, hidden while it is carried, never taking focus: R, arrows, Cmd+D and Delete keep working because the painter's key handler ignores popovers but not dialogs or menus). The pointer: Shift draws a straight line from the last painted cell, the right button erases on the layer the tool paints, Alt/Cmd is the eyedropper, space or the middle button pans, Ctrl+wheel zooms; arrows nudge the selected prop (quick repeats are one undo step: `useHistory.set(update, mergeKey)`). A `TooltipTrigger asChild` around a toggle replaces its `data-state` ("closed"), so style armed toggles with `aria-checked:`, never `data-[state=on]:`. **Space profile** (`catalog.space`, `docs/guides/volume/04-scenery-kits.md` §1, §3.2): when the profile puts walls on borders (`wallPlacement(catalog) === 'border'`, the jrpg preset) a scene's `walls` grid is `(rows + 1) × (cols + 1)` and an entry is the **vertex** at the top-left corner of a cell. `edit.ts` reads that from the scene (`wallsOnBorders`: `walls.length > rows`), so `paint`, `removeMany`, `pickAt`, `resize`, `withLayers` and the gestures work on vertices for walls and on cells for everything else; a stroke of walls follows `vertexPath` (4-connected, a diagonal goes through a corner vertex, so a run is never a string of loose posts). The canvas takes the vertex nearest the pointer (`render.ts: vertexFromPoint`) for the wall brush and the wall eraser, marks it with a dot and shows the wall piece as a ghost on it; catalogs without `space` keep walls through cell centres and the old behaviour. Use the engine's `emptyScene(catalog, cols, rows)` (re-exported by `edit.ts`) for every new scene, never your own arrays. A scene saved for the other placement fails `validateScene`: the painter says so and stays on the last good picture. **Wall heights:** a piece with `heights` (`['wall', 'fence']`) is painted at the height chosen in the tool-options bar (`HeightSelect`, labels in `labels.ts: heightLabel`); the default height is stored as the plain id, another as `{ piece, height }`, repainting a cell keeps its variant and options, and the eyedropper takes the height too. **Scale figures** (`SceneData.figures`, `toggleFigure`): the "Scale figure" tool (M) shows a translucent mannequin of the profile's character height in the hovered cell (drawn by the overlay with `scaleFigure`) and a click pins one in the scene (the engine draws pinned figures; exported reference images leave them out). **Everything is selectable, and by its picture** (`Selection` in `edit.ts`: a prop, a wall (its cell, or vertex on borders), a scale figure or a floor cell; `validSelection` drops one that points at nothing): `lib/scenery/hit.ts` lays the scene out like the drawing and reads the renderer's own frames, and `SceneCanvas.targetAt` takes what is seen under the pointer: a figure's box, else the top-most prop or wall picture with a solid pixel (like the playground's alpha pick), else a wall on the nearest vertex, else the floor of the cell. Hover and selection are outlined by a rim round the picture's silhouette (`overlay.ts: Mark`), plus the footprint, the wall's vertex ring or the figure's box. `selection-popover.tsx` shows the popover for the kind selected (prop: direction, look, options, copy; wall: height, look, options, "Paint with this"; floor: "Paint with this", clear; figure: delete); Delete takes out whatever is selected, arrows nudge props, walls and figures, and dragging with the select tool moves a prop, a wall (`move-wall`: the run it joins redraws live, a taken or outside vertex is refused) or a figure (`move-figure`), one undo step each. **The eraser takes whatever is on top** under the pointer, whatever its type (default layer "Everything"; Floor / Walls / Props, which includes figures, restrict it): a `sweep` stroke (`gesture.ts`) samples the pointer every few pixels along the drag and removes the top-most thing there, leaving the floor of a cell whose prop it just took; all the samples of one pointer event are looked up against the same scene and removed in one edit (`sweepSpots` → `removeMany`), so a fast stroke builds the sprite list once per event, not once per sample; the right button does the same for the tool's layer. A variant is chosen or automatic (`variant` omitted: the engine picks the look from the position, which is what "Automatic" means in every variant select); never store 0 to mean "default". **Warm-up** (`lib/scenery/warm.ts`): the engine rasterizes frames in software and a floor's transitions cost most of a second the first time, so the pieces the three brushes hold are drawn into the renderer's cache in idle callbacks, a few frames at a time, as soon as they are armed. It is deliberately small (`framesOf`: a floor's full tile per variant, the masks of a straight run for walls and fences at the default height, the facings of a prop, at most 32 frames a piece) and polite: it waits while the pointer has been active in the last 600 ms (`touched` ref in `SceneCanvas`) and while the renderer is not yet at the canvas's scale, 8 ms per callback; everything else is drawn when first used. "Save scene" posts `new-scene` to `/__api/cli` (outfits and scenes both travel as a temp file; it writes `src/scenes/<name>.ts` and `sheets/scenes/<name>.ts`) and exports `scenes/<name>`. **Living scenery** (`docs/guides/volume/05-living-scenery.md`): pieces have `states` and `clips`, doors (`group: 'door'`) stand on cell edges and the engine exports navigation. *Painter:* a door tool (D) puts a door on the edge nearest the pointer (`render.ts: edgeFromPoint`, outer border included), with a ghost on the edge, R (or the Side button) turning it to its other side (`edit.ts: placeDoor`, `flipDoor`; a flipped door stores `dir`, the default side stores none), never on an edge that has one (`doorAt`); a door is a placement with `edge`, so `moveProp`, `setDirection` and `duplicateProp` leave doors alone and `moveDoor`, `flipDoor` and `nudgeSelected` move them (the `move-door` stroke follows the pointer's edges); picking, selecting and erasing work by the picture as for props (`hit.ts` keys doors by edge too). The options bar and the selection popover have a state select for any piece with `states` (`StateSelect`; the first state is the default and is not stored: `edit.ts: setState`, `placeProp({ state })`). The toolbar's route button draws the scene's navigation over it (`lib/scenery/nav-draw.ts`: red cells block, amber is slow, blue is where a thing is used from, thick lines are blocked edges, dots are wall posts (piers, pillars: `nav.posts`), green a door that lets through; `navigation.ts` keeps `sceneNavigation` per scene object). Door thumbnails show the door between two posts of its wall. *Playground:* a chosen scene is a `World` (`lib/scenery/background.ts: sceneWorldQuery`, `?fixture=true` offers the built-in kit's scene): its floors and decals are drawn once at the export scale as the ground (a zoom only scales it with hard edges, like the characters, so no frame is drawn again), and everything that stands (walls, fences, doors, props) is drawn every frame from the engine renderer and **sorted in among the actors by the y of its pivot** (`scene.tsx` merges `live.standing` with the actors sorted by `y`). The engine and `lib/scenery/living.ts` load with the first scene (`World.living`). `living.ts` is pure and tested (`tests/viewer/living.test.ts`): `startLive` lays the scene out and makes its navigation, `play`/`stepLive` run clips (events fire as frames pass; a door lets through from its `open` event, and a transition that ends leaves the piece resting in its `to` state and makes the navigation again), `drawnItem` gives the frame to draw (a clip's while it plays, a loop's always), `usableFrom`/`use` pick the nearest thing whose use-cells hold the character (the E key and the HUD button; the clip is found by `transitionFrom`, by what it does — the one that starts in the piece's state and ends in another, the one leading to the next state winning — never by its name, because kits name them by action: `opening`, `closing`, `pulling`, `breaking`), `strike` breaks what a blow from a `hit` event lands on, `constrain` moves a step with `moveIn` so the controlled character slides along walls and stops a body's width (`BODY_RADIUS`) short of them and of shut doors (the runtime's `moveIn` also keeps it clear of wall posts and takes long steps in half-cell pieces), `spawnPoint`/`standable` put it on the floor. Characters and the scene share *actor units* (exported pixels): `Mapping` converts both ways (`toWorld`, `toView`); the scene is centred in the view, so when the zoom or the window moves it every actor and effect is shifted with it, and a refetch of the catalog (any file change) that brings the same scene keeps the one being played (open doors, broken urns). "Clear scene" starts the scene again. The HUD shows the last thing a piece did and what E would do; the toolbar has the same navigation overlay.
- **Previews by what the asset is** (`components/preview/preview-dialog.tsx` picks the body by `roleOf`; the header and `[` / `]` live in `preview-shell.tsx`): anything animated plays in the generic player (stage, transport, inspector). An **effect** (`vfx-section.tsx`) uses it with its own section (kind, layer, how far below the origin its floor marks are, reach, speed and range, the effect it `follows` as a button to open it), a dashed ring of its `size` (`size × meta.scale` exported px, toggle), and for a projectile a flight simulation along the chosen row at `travel.speed` with the depth shrunk by sin(tilt) (the stage wrapper is moved in an animation frame, memoized so the player's renders do not restart it); events come from `meta.data.effect.events` (`lib/atlas.ts: eventsOf`) and the direction is the compass for eight facings, a slider for more. An **item icon** (`icon-preview.tsx`) is an inventory: the project's icons in a grid of slots starting at the chosen one, each slot ringed in its rarity's color and numbered by its stack, with the item's data and the project's rarity legend; when the project has a slot sheet (`kind: 'slot'`, `states` empty/hover/selected, `data.content` the margin round the well) the slots are drawn with it at its native size and each icon sits in the box the margins leave. An **interface piece** (`ui-preview.tsx`, geometry from `@diorama/runtime`, `packages/runtime/src/ui.ts`, tested in `tests/runtime/ui.test.ts`) is shown the way a game uses it: a nine-slice is stretched with width and height sliders or the corner handle (`nineSlice`: corners keep their size, edges stretch along, the middle both ways; state toggle; the inset lines as a switch), a bar is drawn the way core/ui.ts says (frames found by the names in `layers`): back, the fill clipped to the value inside its `fillBox` along `grows`, the `cap` (a frame with the bright edge at the full end of the box, moved back by what is missing from the value and clipped to the box: `capPlacement`), then the frame; it can be made longer (the fill box grows with it; 1% still shows the cap), a bitmap font sets text glyph by glyph with its `advances` and spacing (`layoutText`), a cursor or image shows its states and its hotspot (`pivot`) and a cursor can be tried over targets.
- **Effects in the playground** (the runtime's `packages/runtime/src/effects.ts`, tested in `tests/runtime/effects.test.ts`; `lib/playground/vfx.ts` shows them in the view in actor units, tested in `tests/viewer/vfx.test.ts`; contract §5 rule 9): the library has the project's effect sheets (`Library.effects`, by id; they, item icons and interface pieces are never listed as objects to place) and a character carries its cues (`meta.data.character.effects` by clip key: `on` an event, or `start` / `end` of the action, which `actor.ts` emits besides the sheet's events). `playCues` turns an event into the effects to play: `stay` at the socket where it fired (`at`, else the `spawn:<socket>` of the frame, else `center`; `feet` is the pivot), `follow` tracking the socket frame by frame, `fly` along the facing the action started with at `travel.speed × scale` (depth shrunk by sin(tilt) of the character's camera) using the sheet's row nearest the heading. A looping effect ends with the action it was cued in. A projectile ends at `travel.range`, at the edge of the view or where the scene stops it (`living.ts: flightStop`: a cell that cannot be entered, a wall or a shut door, followed in steps of a fraction of a cell), and plays the effect it `follows` there. Layers: `ground` effects are drawn under everything that stands, `air` ones are sorted with the actors and the scene's things by the floor point under their origin: the socket's position with its height dropped (`liftAt`: the actor's floor point less the socket's y; a following effect updates it every frame), **never** the socket lowered by the effect's own `height`, which only says how far below the origin its floor marks are drawn (the origin goes on the socket). `stay` and `follow` show the sheet row nearest the actor's facing, `fly` the row nearest its heading; `end` also fires for a clip that holds its last frame. The generic rings (`effects.ts`) are drawn only for a character without cues, or for an event whose cued sheets are missing from the project.
