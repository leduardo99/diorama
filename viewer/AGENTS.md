# Diorama viewer

React SPA on the TanStack stack (Router, Query, Table, Store), served by Vite at `/viewer/`.
Its API is the `diorama-api` plugin in `vite.config.ts`; the filesystem logic (catalog, delete, trash, restore) and the commands of `/__api/cli` (`cli-args.ts`) are in `viewer/server/`.

## Projects and paths

- The viewer's projects are the folders of `projects/`, the user's own, and nothing else: `viewer/server/catalog.ts` lists them with `listProjects(repo, VIEWER_ROOTS)` and `viewer/server/assets-fs.ts` finds them with `findProject(name, repo, VIEWER_ROOTS)` (`tools/project.ts`), so a sample of `examples/` is never listed, opened, deleted or saved into, whatever its name. The samples ship with Diorama; `npm run example` copies the sample to `projects/<sample>` and exports it there (`SAMPLE_PROJECT` in `lib/mutations.ts` is its name), and from then on it is a project like any other. Every API is keyed by the project's name, and `viewer/server/cli-args.ts` (`cliArgs`, tested in `tests/viewer/cli-args.test.ts`) hands the commands of `/__api/cli` the project as `projects/<name>` (a bare name would find `examples/<name>` when no project of that name is left). With no project, the index route (`routes/index.tsx`) is an `Empty`: what Diorama is, "New project" (the New dialog) and "Try the sample", which posts `example` to `/__api/cli` (`useTrySample` in `lib/mutations.ts`: it reads the catalog every second while it runs, to show the copy and its exports coming in, then opens the project, but only if the user is still on the start page; elsewhere its toast offers "Open <sample>"), with the command to copy for a terminal. `npm run example` runs one at a time (`tools/lock.ts`, `projects/.example.lock`): `/__api/example-run` (`exampleRunQuery`) says whether a run is going on, from this server, a terminal or another tab, and the empty state then shows it running and starts no second one; the plugin answers a second `example` with 409 `running: true` without starting it. When the copy is in the catalog and nothing runs (a run whose export failed, or one that ended elsewhere), the headline says the sample is in your projects and "Open <sample>" takes the place of "Try the sample", or sits in the failure's alert, where "Try the sample" stays to export what is missing.
- A project is `src/` (code), `sheets/` (one file per exported sheet: every `.ts` there is a sheet), `assets/` (the exports, at their sheet's own path: `sheets/gear/helm.ts` → `assets/gear/helm.png`) and `review/` (scratch: the viewer never reads it). `viewer/server/catalog.ts` reads `sheets/` and `assets/`; `src/` is read for what a sheet imports and for the kit catalogs. Paths and URLs are built with `lib/project-paths.ts` (`projectDir`, `projectFile`, `projectUrl`, `kitCatalogUrl`, `sceneUrl`), never by hand: files are served at `/projects/<project>/...` (`/projects/my-game/assets/gear/helm.png`).
- A project may have a game, `game/index.html` (rule 8 of `docs/ARCHITECTURE.md`), which the server reports as `ProjectMeta.hasGame`: the project bar's "Play game" and the ⋯ menu's "Open game" open it in a new tab with a plain `<a target="_blank" rel="noopener">` to `projectUrl(name, 'game/')`, never a router `Link` (the game is a page of its own, not a route of the viewer).
- The kit catalogs the viewer imports are `src/gear/catalog.ts` (`CATALOG`, `CHARACTERS`) and `src/scenery/catalog.ts` (`SCENERY`); saved scenes are `src/scenes/<name>.ts` (`SCENE`). `src/vfx/catalog.ts` and `src/items/catalog.ts` are read by the commands that write `sheets/vfx/` and `sheets/icons/`, not by the viewer, which shows effects and item icons from their exported atlases. Exported folders: `characters/<id>/`, `props/`, `scenes/`, `ui/`, and the generated `gear/`, `scenery/`, `vfx/`, `icons/`.
- The viewer's deletes go to `<repo>/.diorama-trash/` (`assets/<project>/<id>/` for assets and sheets, `projects/<id>/<project>` for a project), outside every project: a project root holds only `src/`, `sheets/`, `assets/`, `review/` and a few files (`npm run check`). Restoring an asset refuses when the project of that name now lives elsewhere (an entry deleted from a sample before the viewer stopped listing them names `examples/`). A project's trash is `tools/trash.ts` (`deleteProject`, `restoreProject`, re-exported by `assets-fs.ts`), which `npm run example -- --force` uses too for the copy it replaces; it then prints how to get that copy back (move the fresh copy out of the way first: `restoreProject` refuses while a project of that name is in `projects/`).

## Conventions

- Routes are file-based in `src/routes/`. `src/routeTree.gen.ts` is generated: never edit it by hand. In `vite.config.ts` the router plugin must stay before the React plugin. A path under a project that matches no section (`/p/my-game/nope`) reaches the project's `notFoundComponent`, which says "Page not found"; "Project not found" is only for the `notFound({ data })` its `beforeLoad` throws.
- The app shell is a header, not a sidebar (`components/app-header.tsx`): logo, the project switcher (`project-switcher.tsx`: a Popover with shadcn `Command`, search, asset counts, "New project", ⌘K; switching keeps the section the user is in, `lib/sections.ts`), the project's ⋯ menu (`project-menu.tsx`: new asset, export, open game, copy path, delete) and New / Refresh catalog / Shortcuts and the language switch (`language-switch.tsx`) on the right. "Shortcuts" (or `?`) is a window (`modals/shortcuts-modal.tsx`): the keys of every page ("Anywhere": N, ⌘K, ?) on top, then one tab per section in the project bar's order (Assets, Playground, Customize, Scenery), open on the section the user is in. Its lists are data, `lib/shortcuts.ts` (`SHORTCUTS`, drawn by `components/shortcut-list.tsx`, which the painter's keyboard popover uses too), and the handlers read their keys from exported sets (`hotkeys.ts: APP_KEYS`, `historyCommand`; `lib/playground/keys.ts`; `lib/scenery/keys.ts` with `TOOL_KEYS`): `tests/viewer/shortcuts.test.ts` checks that every key in those sets has a row and that no row shows a key nothing reads, so a key added to a handler goes in its set and in the list. A page that shows some of its keys itself takes their caps from the same lists (`capsFor`): the Playground's palette (`lib/playground/controls.ts`: the controlled character's keys with the clip each plays, ⇧ and the arrows as the window writes them, [ ] in the picker's label, and the scene's keys in the "Place in the scene" hint, the right button said as the window says it). ⌘ stands for "⌘ or Ctrl" wherever the handler takes both. `N` and `?` (`routes/__root.tsx`) wait while a modal dialog or a menu is open (`isModalOpen`), not for a popover, so they work while something is selected in the Playground or the painter. The project's own bar (`routes/p.$project.tsx`) holds its section tabs, its totals (its assets and the size of their images, then the sheets not exported yet while there are any: `lib/export-state.ts: projectTotals`; a sheet exports to one asset, so the sheets are not a second count) and Play game (when `hasGame`) / Export / New asset. Export opens the New dialog on its Export tab, the only tab with a description (what an export draws and where); the button's tooltip is that same sentence. No label names a command-line flag (`tests/viewer/i18n.test.ts` checks every string): the CLI line under the fields is the command itself, and `tools/export.ts` prints its tip about `--grid` only at a terminal, so the output the dialog shows never has it. Pages fill the space under the header (`flex min-h-0 flex-1 flex-col`), nothing scrolls but their own scroll element.
- The URL is the state of a project's asset list (search, sort, filters, view, grouping, open Details window). Search params are validated with zod in `src/lib/search.ts`; components read them with `getRouteApi` (`src/lib/routes.ts`), never with casts.
- Server state lives in TanStack Query (`src/lib/queries.ts`, `src/lib/mutations.ts`). Callbacks that must outlive a menu or dialog go on `useMutation`, not on `mutate()`.
- Table is v9, not v8: `features` and `columns` are module-scope (`src/lib/asset-columns.tsx`), sorting and filters are controlled from the URL (`src/lib/use-asset-table.ts`).
- UI is shadcn/ui (radix base, `mira` preset, Tailwind v4): components live in `src/components/ui/` and are added with `npx shadcn@latest add <name>`, never written by hand. The shadcn CLI is not a dependency of the project (npx downloads it on each use; the components here were added with 4.22.1, so `npx shadcn@4.22.1 add <name>` matches them). The stylesheet the components need, which the package used to provide as `shadcn/tailwind.css`, is copied into `src/styles/shadcn-tailwind.css` and imported by `styles/app.css`; when components come from a newer CLI, copy that version's `dist/tailwind.css` over it (keep the header) and update the version there and in `THIRD_PARTY.md`. Load the `shadcn` skill (`.claude/skills/shadcn`) before touching UI and follow its rules: semantic colors, `gap-*`, `data-icon`, Field/FieldGroup for forms, AlertDialog for destructive confirms, Empty/Alert/Badge/Skeleton instead of custom markup.
- React rules: load the `vercel-react-best-practices` skill (`.claude/skills/react-best-practices`, a copy of `vercel-labs/agent-skills` at commit `063bee9`; rules in `rules/*.md`) before writing or changing components. What matters most here: gesture and pointer state in refs (`rerender-use-ref-transient-values`), derived values during render and not in effects (`rerender-derived-state-no-effect`), functional `setState`, lazy `useState`/`useHistory` initializers, `memo` only where a re-render was measured to cost (the palette rows, the canvas), stable callbacks for memoized children, no components defined inside components, non-passive `wheel` only where `preventDefault` is needed.
- Modals are `@ebay/nice-modal-react` modals in `src/modals/`: open them from anywhere with `NiceModal.show(Modal, props)`; the single `NiceModal.Provider` is in `routes/__root.tsx`. Bind a shadcn Dialog with `useModalDialog()`, which also gives the focus back on close: Radix returns it only to a `DialogTrigger`, which a modal shown with `NiceModal.show()` has not got, so the hook keeps what had the focus when the modal was shown (for an item of a menu or a popover, the button that opened that) and focuses it again if it is still on the page.
- Toasts are `sonner` (`toast()`); there is no custom toast store.
- **Interface language** (`src/i18n/`): English by default and Brazilian Portuguese; the header switch (`language-switch.tsx`) is remembered in `localStorage` (`diorama.lang`) and sets `<html lang>`. The Phaser test bench reads the same key for its footer (`packages/phaser/demo/footer.ts`), so keep its name. **Every interface string goes through `t()`, with its key in both dictionaries**: `en.ts` is the source of truth (nested keys, `as const`) and `pt-BR.ts` is typed against its shape, so a missing or extra key is a type error. Labels, buttons, tooltips, `aria-label`s, `title`s, placeholders, toasts, errors, empty states, the sentences the viewer writes (the wield notes) and units all count; English copy is sentence case with no exclamation marks. `tests/viewer/i18n.test.ts` checks the keys, the `{placeholders}`, the plurals and that no Portuguese is left hard-coded in `src/` (its `ALLOWED` list takes text that is legitimately content). Portuguese says each term one way, and the same test holds the glossary (`GLOSSARY`): clip is clipe, fit is ajustar and add-on is complemento, while frame, slot and Sockets stay in English, as do asset, sheet (masculine: o sheet, os sheets), sprite, atlas, prop, outfit, kit, Playground, Customize's preview and export as a noun (o export).
  - In components: `const { t, plural, number, date, relative, bytes, list } = useT()`, with `t('key', { name })`, `plural('counts.assets', n)` (a key with `.one` and `.other`, picked by `Intl.PluralRules`) and the formatters: never `toFixed` or `toLocaleString` by hand. A sentence with `<code>`, `<kbd>`, `<b>` or `<mono>` in it is rendered by `<Rich id="..." />`, never cut in pieces in the JSX.
  - Pure code in `lib/` that writes text takes a translator (`wieldReport(..., translator)`, `groupLabel(t, group)`), so a test picks the language with `createTranslator('pt-BR')` (`i18n/core.ts`: no React, no DOM); code outside a component (a thrown error, a toast from a callback) uses `currentTranslator()` from `i18n/store.ts`. A memo that holds text lists `t` in its dependencies.
  - What comes from the project's data (catalog labels, item and scene names, the engine's messages, the server's errors) is content: shown as it is, never put in the dictionaries. The shadcn `dialog`, `sheet`, `spinner` and `breadcrumb` read their screen-reader texts with `useT()`: put that back if one is added again with the CLI.
- Tailwind only scans `viewer/src` (`source("../")` in `styles/app.css`). Do not widen it: scanning the repo reloads the page on every edit elsewhere.
- The `diorama-api` plugin redirects a game's address without its slash (`/projects/my-game/game`) to `game/`, and the Phaser test bench's (`/packages/phaser/demo`) to `demo/`: Vite would serve the repository's root page for them, which sends you to the viewer. Edits under `packages/phaser/` reload only the test bench and the game pages of every folder of `projects/` and `examples/` (`hotUpdate`).
- The plugin's `hotUpdate` in `vite.config.ts` keeps the files of projects (`projects/`, and the samples of `examples/`, which the commands still export in place), `core/`, `templates/` and `tools/` from reloading the viewer when they are changed, created or deleted (Vite 6 calls `hotUpdate` for all three; the older `handleHotUpdate` only saw changes, so "Delete project" or `npm run example` reloaded the page); a file under `projects/<p>/assets|sheets|src/` tells the open viewer to refetch instead (not one of a dot folder, like the copy `example` makes before renaming it into place); a reload would drop the toasts that carry Undo and the progress of "Try the sample". A project's game page is still reloaded, alone. After editing `core/`, reload the page by hand.
- The playground (`src/lib/playground/*`, `src/components/playground/*`) reads only exported atlases (when the project has a game, a line under its toolbar says the Playground plays the exports with debug tools and `game/` plays them in Phaser, with a "Play game" link) and follows the action contract in `docs/guides/rig/04-atlas-contract.md`: a character is `meta.data.character` (manifest with `controls`) or, for old atlases, a folder + `meta.data.skeleton` + `meta.pivot`; clips are classified by `meta.data.clipKind`/`action`/`key`/`tags`/`hold`/`travel`/`sockets`/`events` (fallback: `groundSpeed`/`loop`), never by file name. Keys come from `controls` (WASD, Shift = last of `move`, 1..9 = `actions` in order, H hit, K death, R reset); the handlers read them from `lib/playground/keys.ts` (`PLAYGROUND_KEYS`, `SEARCH_KEYS`, `actionIndexOf`, and `inputOf` for the way held keys move the character). The state machine is the runtime's (`@diorama/runtime`, `packages/runtime/src/actor.ts`, in floor world units: priority death>hit>actions>locomotion>idle, an action is replaced only from its `cancel` event, hit/death interrupt anything, `hold` freezes until reset, `travel` follows the facing the action started with); `actor.ts` puts its actors in the view (`view.ts` gives each one `x`, `y` in actor units, projected with its character's camera at its export scale; a point the view sets (a spawn, a drag, a move it clamps) reads back exactly, and `vfx.ts` draws an effect where the view draws the frame that cued it (on its socket: the actor less the pivot plus the socket × scale), moves a projectile by its velocity in actor units, turns its impact to the heading that velocity shows and sorts an effect at `y + lift`, so half pixels, the draw order's ties and an impact's row come out as they did in px; `currentFrame` pivots the rectangle the view draws (without `meta.pivot`, the middle of its bottom, trimmed or not); a clip moves its sprite at its own `meta.scale` and a projectile flies at its effect sheet's; the view's sides are kept by `sideRoom`; `startClip`, `stepPlayer` and `advance` emit the events the runtime returns) and `effects.ts` draws events: `hit` rings at the weapon socket (`tip`, else `mouth`, else `hand`), `release` sends a projectile from `spawn:<socket>` (it ends after 150 logical px or when it leaves the scene, with a ring where it landed), and skills tagged `aoe` draw nothing because their sheet already has the rings. The looping base clip fires its own events (`step:<leg>`); the HUD ("Now playing") names them only with the toolbar's "Step events" on (a preference, off by default), and otherwise shows the last event that is not a stride, so a hit stays while the character walks away (`actor.ts: hudOf`, `isStep`, recorded for every event `startClip`, `stepPlayer` and `advance` emit; its `reset` forgets it; frames are 0-based, as in the manifest). The scene toolbar has a time scale (1×, ¼×, ⅒×, Pause) to read frames and events; it is never persisted and a badge (click to reset) shows whenever it is not 1×. Its zoom is 1×–4×, or Fit with a scene (`view.ts: fitZoom`, the Details window's rule: the largest whole zoom that fits, at most 4×, else the fraction that fits, with a 48 px margin), worked out from the scene box's size (a `ResizeObserver`), so it stays live when the window or the toolbar changes; choosing a scene sets Fit, and a scene remembered from the last visit keeps the zoom stored with it. Closing the "Scene" select (a pick, Esc, a click outside) hands the keys to the scene: its `onCloseAutoFocus` is prevented and focuses the canvas (`#playground-canvas`, `tabIndex={0}`), because Radix would focus the select again, whose typeahead picks a scene by its letter. The canvas's ring is for the keyboard only: the focus is given with `focusVisible` set by how the list was closed (keys or Esc, not a click), since a browser guesses wrong for a focus given by code; Tailwind's `outline-none` also sets the outline's style, so the ring needs `focus-visible:outline-solid`. The key handlers ignore keydown while a modal dialog or a menu is open (`hotkeys.ts: isModalOpen`; a popover does not count), keyup always lets a held key go, and the digits are read by `e.code` (`Digit1`–`Digit9`, the number pad by its key), so Shift+digit plays an action while running. The rules are tested in `tests/runtime/actor.test.ts`, the view and the rings in `tests/viewer/playground.test.ts`. The runtime moves at `groundSpeed` world units per second and the view draws that at `× meta.scale` with the vertical part multiplied by `sin(camera.tilt)` (manifest `camera`, default 48°; root motion too), so the feet stay planted in every direction while the facing row still follows the input's angle; facing maps the heading to `meta.directionFacings`. `meta.data.character` is a manifest object on character sheets but only the wearer's id (a string) on gear items (`role: 'gear'`): the runtime reads it through `manifestOf` and keeps gear items out of characters (they are objects to place); `library.ts` hands the server's asset list to the runtime's `readSheet` and `buildLibrary`. The palette (`placement-list.tsx`) is virtualized with TanStack Virtual and its search/grouping logic is pure (`lib/playground/catalog.ts`, tested in `tests/viewer/playground.test.ts`); things on the scene are picked by pixel alpha, dragged, and edited through `SceneHandle`.
- The asset grid and table are virtualized with TanStack Virtual (720 assets mount ~15 cards): `AssetsView` owns the scroll element and passes `scrollRef` to both lists; the grid lays out whole rows (`useGridColumns` gives columns and card width, as `auto-fill` would) and the table uses spacer rows under a sticky header. Each list scrolls its own active entry into view; `useEntrySelection` only moves the key.
- The asset list filters by type (`role` in the URL: Characters, Gear, Scenery, Props, Effects, Icons, Interface, Other), read from the atlas (`atlasInfo.role`, `part`, `label`, `group`, `kind`, `rarity`, `stack`, `character` in the catalog; `lib/asset-role.ts`). Gear is called Gear in both languages, never items, parts or pieces: item icons are items, and scenery pieces and the List tab's outfit pieces (gear and body parts together) are pieces. A character has one name everywhere: its manifest's `label` (`AtlasInfo.character`, `{ name, label }` from `meta.data.character`, the label falling back to the id for atlases exported before labels; read it with `characterLabel`), with its folder (`characters/hero`) as secondary text, in Assets (its card, and the Details window's title, `detailsTitle`), the Playground (picker, palette, popover, `HudInfo.character`, from the runtime's `Character.label`), Customize (the kit's `label`, with its id) and the test bench (`packages/phaser/demo/`, the label with its id in a tooltip). Only a character's clips are one entry in the grid and one set of clips in the Details window (`lib/groups.ts`): grouped by its manifest in its folder, as the runtime groups them (an older character sheet without a manifest by its folder), and a character with a single clip is still one. Everything else stands alone, whatever its folder holds: a scenery folder's animated sheets (a door's `--closing`), effects (`role: 'vfx'`, `meta.data.effect`), item icons (`'icon'`, `meta.data.item`) and interface pieces (`'ui'`, `meta.data.kind`); an icon's card shows its rarity tier in the project's color, its kind and its stack, an effect or interface card its kind, and an effect plays on hover like any animated sheet. `roleDetail` is the badge text of every role, in cards and in the table; an effect's kind is in words (`effectKind`, as in the Details window), while an item's or interface piece's kind is shown as the atlas writes it. A gear sheet is titled by its label, carries its group as a badge ("Gear" when it has none), and its thumbnail is the gear cut out of its cell. A card's short counts, "16f · 8d" (frames per direction, directions: `frame-counts.tsx`), say themselves in full in tooltips; the directions are the catalog's `facings`, not the rows (an interface piece's rows are its states, a wall's its heights, a scenery clip's its variants, `facingsOf`), as the count on the Details window's clip tabs does; that tooltip sits on the count inside the tab, never round the tab (a `TooltipTrigger asChild` would take its `data-state`).
- Each asset has an engine, read from the imports of its sheet and of every local file that chain reaches in `src/`, to its end (`tools/sources.ts: createSourceReader`, which `viewer/server/catalog.ts` shares with `npm run export -- --changed`; a sheet is thin, the drawing is several imports deep): `rig` (`@core/rig`: characters, gear, item icons), else `volume` (`@core/volume`: props, scenery, effects), else none (no sheet, or a sheet that reaches neither). The asset list filters and sorts by it (`engine` in the URL, `EngineBadge`, whose tooltip says what the engine is) and the "New → Asset" form offers exactly these two: volume asks for size and fps, rig for a skeleton and a clip and runs `new-asset --engine rig` (the first clip of a character folder creates `src/<folder>/character.ts`; every asset has a sheet in `sheets/<subpath>.ts`, and a volume one its drawing in `src/<subpath>.ts`; subpaths are kebab-case). The viewer shows the assets through the engine's own previews (the Details window, playground, customizer, scenery painter).
- Export state comes from the server catalog: `AssetFileMeta.sourceMtime` (newest of the sheet and the `src/` files it imports, however deep) vs the image's `mtime` gives `isStale` (the rule, with its second of slack, is `tools/freshness.ts`: `export --changed` exports exactly the stale and pending sheets), and `ProjectMeta.pendingSheets` lists sheets with no image at their own path (`src/lib/export-state.ts`, covered by `tests/viewer/catalog.test.ts`; `AssetFileMeta.sheet` is the sheet's path under `sheets/`), which the project bar's totals count as "not exported". `ExportBanner` and `PendingExportModal` export them one by one through `useExportSources`.
- Changes under `viewer/server/` are loaded by `vite.config.ts` at startup: restart `npm run view` after editing the catalog, the API or `cli-args.ts`.
- The customize tab (`src/components/customize/*`, `src/lib/outfit/*`) dresses characters with the project's gear kit and previews them live with the real engine: `drawCharacterFrame`, `outfitFromData` and `validateOutfit` from `@core/rig`. The kit is `projects/<p>/src/gear/catalog.ts` (exports `CATALOG` and `CHARACTERS`), loaded lazily by dynamic import of its path, only when the server catalog says it exists (`ProjectMeta.hasGearKit`, `lib/outfit/catalog.ts`): a kit created while the viewer runs shows up at the next refresh (`import.meta.glob` would not see a file created after the dev server started); a project without it gets an explanation, and `?fixture=true` loads the built-in kit (`lib/outfit/fixture.ts`) to develop without one. Outfit edits are pure functions (`lib/outfit/edit.ts`, tested in `tests/viewer/outfit.test.ts`); drafts live in memory per project and character. A skin is a function: never hand one to `setState` directly (React would call it as an updater), wrap it as `setSkin(() => skin)`. The preview repaints only when the outfit, clip, frame, facing or zoom change, and the eight-direction strip paints one direction at a time. "Save as character" posts `new-outfit-character` to `/__api/cli` (the plugin writes the outfit to a temp file for `tools/cli.ts`) (it writes `src/characters/<name>/{outfit,character}.ts` and `sheets/characters/<name>/<clip>.ts`) and then exports `characters/<name>/`. Parts are loaded when the page opens: reload it after editing the kit. Material roles split in two (`splitRoles`): the kit lists a part's roles with their fallbacks (`['metalAccent', 'metal']`), so a role that extends another of the list is a refinement and lives in a folded "Advanced" section. Exported gear items (`gear/<part>.png`, from `sheets/gear/<part>.ts` written by `gear-items`; `meta.data.role = 'gear'` with `part`, `label`, `group`) are the pickers' thumbnails (the SE_0 cell cut to its drawn pixels, `lib/trim.ts`) and show in the asset list as "Gear"; "Update gear" posts `gear-items` to `/__api/cli` and exports the folder only when something is missing or stale.
- **Customizer by slot** (`components/customize/slot-board.tsx`, `part-picker.tsx`, pure model `lib/outfit/slots.ts`, tested in `tests/viewer/slots.test.ts`): the default "Slots" tab lists the places the skeleton has (`slotsOf` from the engine: a quadruped has no hands; places the kit has nothing for are left out), each with what is worn there, so swapping is one click. A piece's row opens `PartPicker` (shadcn `Command` in a popover, its list computed only while open: search; "Similar" are the engine's `swapCandidates`, the same `equip` slot when the kit sets it, else the same group resting on the same kind of part, then "Others"; "Take off"; for a pair the "On both sides" switch). The edits are the engine's (`swapPiece`, `equipPart`, `removePiece` from `@core/rig/outfit-edit.ts`, guide 05 "Editing outfits": the rules a game shares when it equips an item), wrapped in `lib/outfit/slots.ts` to return `null` instead of throwing and to add what a screen needs: `swapPiece` keeps the piece's place, side, **id** and host, the materials by role and the options by key (numbers clamped, selects validated); what rested on it stays when it needs no host (a belt on a tunic that becomes a tabard) or accepts the new part, and an add-on that cannot rest on it goes, with a toast and "Undo"; `removePiece` frees the pieces that did not need their host instead of removing them. The wrapper asks `swapBlocker` before a swap: a part whose `equip` slot another piece keeps is a candidate marked `taken` ("Slot taken by …", disabled; the engine's `swapPiece` throws on it), and one that needs the hands (a two-handed weapon beside a shield) is not refused but done with `equipPart`, which takes the other hand's piece out (`pushed`, said in the picker as "Takes … out of the hands" and in the toast with "Undo"). The engine also puts a piece after a host that comes later in the list. An empty place offers "Equip" (`equipOrSwap`: a part with `equip` replaces the piece that keeps that slot, one without stacks as a layer; an add-on needs its `requires` host worn and is disabled with "Needs: …"; a part whose `equip` another piece keeps is "Slot taken by …"). The property tests run every swap and every equip the picker can offer, for every character of the real kit, through `validateOutfit`, so a kit change that breaks a rule fails there instead of in the UI. Every edit goes through `useDraft` (a `useHistory`: undo/redo buttons and ⌘Z / ⇧⌘Z / Ctrl+Y, read by `hotkeys.ts: historyCommand` as in the painter, sliders merge into one step with a merge key). **Weapons** (`lib/outfit/wield.ts`, tested in `tests/viewer/wield.test.ts`): a held part says its class (`PartInfo.wield`), a character's attacks say the classes they are made for (`CharacterClip.wields`), each hand (slots hand and forearm) holds one part with `wield`, and after every edit `wieldReport` (the engine's `checkWield` in the words of the screen) tells in an alert above the pieces when no clip is made for what is held or a held item is never swung; the preview's clip picker marks the clips made for something else (they still play there) and the save dialog lists the clips the new character will not get (`new-outfit-character` only generates the usable ones). The test keeps the report and the engine agreeing on when there is something to say, over every swap the picker offers. The viewer has no use for socket data (`weaponSockets` is applied when the character is exported), and the playground never plays a clip the manifest marks `usable: false` (the runtime's `buildLibrary`, `packages/runtime/src/gear.ts: playableClips`). Saved scenes are `src/scenes/<name>.ts` (`SCENE`; a helper beside them, like `map.ts`, exports no `SCENE` and is not a scene), found through the server catalog (`hasSceneryKit`, `scenes`). Edits are pure functions on `SceneData` (`lib/scenery/edit.ts`, which asks the engine for `footprintOf` and `cellPiece` so both always agree) and a drag is a pure stroke (`lib/scenery/gesture.ts`: `startPaint`/`startSweep`/`startMove`/`startMoveWall`/`startMoveFigure`, `advance` for each new cell, `resultOf` for what is committed); both are tested in `tests/viewer/scenery.test.ts`. **Nothing re-renders React while the pointer moves**: `SceneCanvas` keeps the stroke, the hovered cell, the scene on screen and the pending frame in refs, draws the main canvas with the engine's cached renderer (`createSceneRenderer`, one per catalog: frames already drawn are copied, so an edit costs about 1 ms of JS) and the overlay (`lib/scenery/overlay.ts`: grid, hover cell, selection, and the ghost of the prop being placed or dragged, copied from `renderer.frame`) in one `requestAnimationFrame` per change, and commits the gesture once with `onCommit` when the pointer is up (one undo step: `use-history.ts` has no begin/end). A click that places a prop or fills is drawn in the next frame and committed at once. What the canvas reports (hovered cell, last drawing time, drawing error, the size of its box) goes to a TanStack Store (`lib/scenery/status.ts`, read by `canvas-readout.tsx` and the painter's alert with `useSelector`), so only those readouts re-render. Keep it that way: no `setState` in pointer handlers, no `useEffect` that redraws per edit, handlers passed to the memoized `SceneCanvas` and `SceneryPalette` must be stable (`useCallback`). The drawing scale is `render.ts: renderScale(zoom × devicePixelRatio)`, capped at the export scale (2): the canvases keep their size in CSS pixels through `zoom` and `image-rendering: pixelated` upscales them, so a retina screen at 2× zoom still draws 2 device pixels per logical pixel, not 4 (a quarter of the memory and of the cold-frame cost; sprites stay crisp). Sprite coordinates (`hit.ts`, rims, anchors) are in drawing pixels, so convert them to CSS pixels with `zoom / scale`, never with `1 / devicePixelRatio`. Changing the scale drops the renderer's cache, so a change of zoom that moves it draws every frame again once; the renderer holds at most 800 frames (`limit`). **Zoom and Fit:** the zooms are the steps of `render.ts: ZOOMS` (¼× to 4×; −/+, Ctrl+wheel and the toolbar step with `stepZoom`). The painter opens at **Fit** (`fitZoom`: the largest step at which the whole drawing, the room for tall pieces included, fits the canvas box with a 16 px margin); a scene opened from the scene menu or started blank opens fitted, `0` or the Fit button fits again, − / + leave Fit (except past either end, where they change nothing), and the zoom is not remembered (`useState`, not a preference: a zoom that suits one scene and window is wrong for the next). `SceneCanvas` measures its box in a layout effect, before its first drawing, with `offsetWidth`/`offsetHeight` (scrollbars in, so one that comes or goes changes nothing) and a `ResizeObserver`, and reports it as `view` in the status store; the painter selects the fitted step from it, not the box, so a resize re-renders it only when the step changes. Fit is live: hiding the panel or resizing the window refits, and each step it crosses that moves the drawing scale (every step on a 1× screen; on a retina screen only those up to 1×, past which the scale holds at the export scale) draws every frame cold once (most of a second for floor transitions). That is why Fit picks from the steps and never takes the exact fraction the asset window's Fit takes (`use-player.ts`), and why there is no 1.5× (one more scale to draw cold). The drawing is centred in the canvas box (a flex box, `m-auto`, `shrink-0`) and scrolls from its corner when it is larger. A zoom moves the selection's popover anchor in the same commit: until the main canvas is drawn at the new scale, the prop's picture measured at the zoom before is scaled, then it is measured again from the renderer. Hiding a layer leaves it out of the drawing, not out of the scene. Keep it that way when adding controls: measure the canvas box's `getBoundingClientRect().top` across every tool, with the panel open and closed and with the alert shown. There is no selection tab: selecting a prop (select tool, or Alt/Cmd-click with any tool) opens a popover over it (`selection-popover.tsx`, anchored to the prop's picture measured from the renderer's frame, hidden while it is carried, never taking focus: R, arrows, Cmd+D and Delete keep working because the painter's key handler ignores popovers but not dialogs or menus (`lib/scenery/keys.ts: isLayerOpen`, which Space held to pan waits for too, so Space presses a dialog's button)). The pointer: Shift draws a straight line from the last painted cell, the right button erases on the layer the tool paints, Alt/Cmd is the eyedropper, space or the middle button pans, Ctrl+wheel zooms; arrows nudge the selected prop (quick repeats are one undo step: `useHistory.set(update, mergeKey)`). A `TooltipTrigger asChild` around a toggle replaces its `data-state` ("closed"), so style armed toggles with `aria-checked:`, never `data-[state=on]:`. **Space profile** (`catalog.space`, `docs/guides/volume/04-scenery-kits.md` §1, §3.2): when the profile puts walls on borders (`wallPlacement(catalog) === 'border'`, which the presets that put walls on cell borders give) a scene's `walls` grid is `(rows + 1) × (cols + 1)` and an entry is the **vertex** at the top-left corner of a cell. `edit.ts` reads that from the scene (`wallsOnBorders`: `walls.length > rows`), so `paint`, `removeMany`, `pickAt`, `resize`, `withLayers` and the gestures work on vertices for walls and on cells for everything else; a stroke of walls follows `vertexPath` (4-connected, a diagonal goes through a corner vertex, so a run is never a string of loose posts). The canvas takes the vertex nearest the pointer (`render.ts: vertexFromPoint`) for the wall brush and the wall eraser, marks it with a dot and shows the wall piece as a ghost on it; catalogs without `space` keep walls through cell centres and the old behaviour. Use the engine's `emptyScene(catalog, cols, rows)` (re-exported by `edit.ts`) for every new scene, never your own arrays. Hover and selection are outlined by a rim round the picture's silhouette (`overlay.ts: Mark`), plus the footprint, the wall's vertex ring or the figure's box. `selection-popover.tsx` shows the popover for the kind selected (prop: direction, look, options, copy; wall: height, look, options, "Paint with this"; floor: "Paint with this", clear; figure: delete); Delete takes out whatever is selected, arrows nudge props, walls and figures, and dragging with the select tool moves a prop, a wall (`move-wall`: the run it joins redraws live, a taken or outside vertex is refused) or a figure (`move-figure`), one undo step each. **The eraser takes whatever is on top** under the pointer, whatever its type (default layer "Everything"; Floor / Walls / Props, which includes figures, restrict it): a `sweep` stroke (`gesture.ts`) samples the pointer every few pixels along the drag and removes the top-most thing there, leaving the floor of a cell whose prop it just took; all the samples of one pointer event are looked up against the same scene and removed in one edit (`sweepSpots` → `removeMany`), so a fast stroke builds the sprite list once per event, not once per sample; the right button does the same for the tool's layer.
